# 常用专家团与工作流示例

使用 `/herdr-team <需求>` 或当前 harness 的等效显式调用。主 Agent 根据交付物从角色配置中选人，默认 2–4 位。 [Expert_Team.toml](../Expert_Team.toml)

## 选成员

| 角色 | 什么时候加入 | 交付物 |
| --- | --- | --- |
| 主 Agent（当前会话） | 每次开团 | 对接需求、选人、汇报和验收。需求尚不成形时也可承担产品梳理 |
| `product-manager` 产品经理 | 需求模糊、范围或优先级有争议 | 问题陈述、范围与非目标、可测的验收标准 |
| `architect` 架构师 | 涉及公共接口、兼容性、跨模块设计或工程标准 | 代码依据、方案取舍及需要解决的风险。需要时再审查实现 |
| `researcher` 信息调研 | 需要外部资料、历史实现或规范依据 | 带来源的结论、冲突和不确定项 |
| `engineer` 实现工程师 | 有已确认的跨模块代码交付 | 独立 worktree 中的改动、实际验证结果、剩余风险 |
| `frontend-engineer` 前端工程师 | 改动集中在前端与交互层 | 可运行的界面改动、验证方式和限制 |
| `backend-engineer` 后端工程师 | 改动集中在服务端、接口或数据层 | 服务端实现、迁移与回滚方式、验证结果 |
| `tester` 测试工程师 | 有独立验收、回归或覆盖检查 | 针对候选改动的测试证据和可复现的问题，可按授权补测试 |
| `performance-analyst` 性能分析师 | 有性能指标异常、超时或明确的优化目标 | 基线、热点、根因假设、验证方案与预期收益 |
| `tech-writer` 文档撰写师 | 需要交付面向读者的文档 | 结构与事实一致的文档、未覆盖内容 |

边界明确的功能通常由实现工程师和测试工程师接手。跨模块或公共接口变更，加架构师先评方案。纯设计任务可以只请架构师。`engineer` 与 `frontend-engineer`、`backend-engineer` 是粒度不同的选择：改动横跨前后端或模块边界时用 `engineer`，集中在单侧时用细分角色，不要同时开两位做同一件事。

## 多视角评审

方案有多种可行解，或成本、兼容性、可维护性的权衡明显时，可以同时请两路架构意见，例如 `architect` 与 `architect-codex`；也可以同一模板开两个会话，只在任务里给不同视角。两路的职责、授权和验收条件保持一致，差别只在 harness、模型或你要它回答的问题。

1. 派工给每位专家同一份原始需求、必要证据和验收条件。任务里写明各自的视角、要回答的问题，以及首轮独立完成：先不要联系其他专家，也不要参考别人的回报，避免判断趋同。
2. 收齐后逐条对齐：议题、各方结论、依据、是否冲突。冲突处自己回到代码或文档核实，不按票数取舍，也不拼接三份报告了事。
3. 输出综合方案、分歧表和你的建议，把需要拍板的差异交给用户。
4. 只剩事实性分歧时，例如一方说有调用方、另一方说没有，再让双方带证据对话一轮，你核对最终结论。
5. 默认两路。第三路留给高风险变更或用户明确要求，并先说明额外成本。

## 方案与实施

1. 确认任务属于哪个 Git 仓库，记录起始提交、当前工作状态和相关项目规则。需要独立架构意见时，给架构师原始需求和必要背景，等它先给证据和判断，再汇总你的方案。
2. 在方案里列出验收条件、候选改动存放方式、所选角色及模型配置和允许执行的验证。模型继承 harness 默认值时照实标明。若需要带入用户已有未提交改动，说明如何带入并由用户确认。获得明确确认后再改代码、补测试和建立实施 worktree。
3. 从已确认的提交创建独立 Git worktree，把原仓库适用的规则和完整任务交给实现工程师。移交至少包含改动范围、接口或行为约定、相关文件、验收条件和可执行的验证。同一工作目录同一时刻只保留一位写入专家，等实现停稳后再交给测试工程师；需要并行时给每位独立 worktree。
4. 让测试工程师在同一候选 worktree 独立验证，以验收条件和实际代码为准。记录实际受测提交，以及有未提交改动时的 diff 范围。测试工程师可在授权范围内新增或修改测试及测试数据，发现产品代码问题可直接向实现工程师发证据，并把对交付有影响的发现回报主 Agent。需要修复时由主 Agent 协调同一 worktree 的写入顺序，修复后复验受影响的项目。
5. 自己检查候选 diff 和证据，确认每条验收条件是否满足。验证命令及提交、集成和发布操作按用户授权与项目规则执行。分别报告通过、失败和未运行的验证，给出 worktree、分支或提交位置。各专家在整项任务期间保持待命，结束时按通用流程回收。 [通用流程](setup.md#待命与收尾)

## 返工归属

评审或测试发现的问题、用户决定后的追加改动，默认退回原作者，不另开同角色专家。作者已经读过仓库、跑过验证、知道取舍，返工只需补新证据；新开一位等于把这些上下文丢掉重来，还要重新交代范围，容易给出和原作者冲突的改法。

复用前用 `hc ls` 和 `hc get <地址>` 核对角色、工作目录和协作编号。同一 worktree 同一时刻只允许一位写入专家，确认原作者已经停稳再派。用 `hc send --json` 发送新的交接编号、上一轮结论、本次证据、授权范围和验收条件，并核对该编号的 `READY`。 [派工与恢复](setup.md#交接与回报)

这些情况不退回原作者，直接新开：

- 需要独立判断。验收不能由作者自己做，兼听也不能拿已经表过态的判断当第二路意见。
- 上下文已被带偏。作者按错误前提干了很久，继续追问会顺着原思路走，换新会话并重写交接更省事。
- 授权、角色或 worktree 不同。只读审计和写入修复是两码事；返工要落到另一个 worktree 时，也得按新写入口径派。
- 原会话已经很长。上下文快到上限时，接着追问会丢前面的细节，不如让作者先写一份结论再重开。

## 其他常用专家团

下面几组是常见组合，按交付物裁剪，不必全开。每组都遵守通用流程：先只读调查、方案经用户确认、写入串行、你负责核对产物。

### 性能诊断团

`performance-analyst` → `engineer` → `tester`，涉及公共接口或结构性改动时先加 `architect`。

1. 先定基线和场景：哪台机器、哪个版本、什么负载、用什么数据对比。
2. 分析师给热点、根因假设和验证方法。一次只验证一个假设，其余挂在待办。
3. 主 Agent 选定假设后交实现工程师，只改授权范围。
4. 测试工程师用同一场景复测，记录前后指标差值和未解释部分。
5. 汇报基线、改动、复测结果和仍未定位的部分。

关键约束：先测量后改动；没有基线不做优化结论；每次只动一个变量，否则复测结果无法归因。

### 方案预研团

`product-manager` + `researcher` + 两路 `architect`（兼听）。全程只读，不产生代码改动。

1. 产品经理定问题、范围、非目标和验收标准。
2. 调研专家补外部资料、规范依据和同类实现，标出来源与不确定项。
3. 两路架构师各自独立给方案，按多视角评审汇总。
4. 主 Agent 产出决策备忘录：问题、候选方案、分歧表、建议和待验证项。
5. 交用户决策后再决定是否进入实施。

关键约束：预研阶段不建 worktree、不改代码；方案里的假设要么标注待验证，要么先由调研专家补证据。

### 前后端联调团

`architect`（接口契约）+ `frontend-engineer` + `backend-engineer` + `tester`。

1. 架构师先定接口、错误码和兼容性约定，作为双方共同依据。
2. 前后端各自在独立 worktree 实现，按契约对接，不经对方目录。
3. 需要改契约时先回架构师确认，由主 Agent 通知双方，不私自变更。
4. 测试工程师用实际接口和界面验证，联调问题由主 Agent 分配归属。
5. 汇报契约版本、两侧改动位置、联调结果和遗留差异。

关键约束：契约先冻结再并行；两侧都不许改对方的目录；契约变更必须回到架构师。

### 文档交付团

`tech-writer` + 事实来源角色（`engineer`、`architect` 或 `performance-analyst`）。

1. 主 Agent 先定目标读者、必须覆盖的事实和使用场景。
2. 事实来源角色提供结论、代码位置和限制，写入交接。
3. 撰写师成稿，只改授权文档文件，未确认处标注待补。
4. 事实来源角色或主 Agent 核对准确性，重点看命令、路径和配置项。
5. 汇报文档位置、章节结构、未覆盖内容。

关键约束：撰写师不臆造事实；有争议的结论回到来源角色；文档里的命令要能照抄执行。
